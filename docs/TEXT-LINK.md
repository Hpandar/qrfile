# qrfile

把**文本文件**变成二维码图片，再还原回**字节完全一致**的文件。适合离线 / 气隙（air-gap）环境下的文件搬运与纸质归档：屏幕显示或打印，手机扫回来。

```
qrfile plan   ./mysrc                              先看看要出多少张码、要扫多久
qrfile encode ./mysrc -o ./qrout --contact-sheet   编码（每张码都自解码比对）
qrfile decode ./qrout -o ./restored                还原（任何一片不合格就不写盘）
qrfile verify ./mysrc ./qrout                      复核：源 ⇄ 码 双向比对
```

> **两台机器只能互相看屏幕？** 实时链路只用两条命令：
> A 机器 `qrfile push <路径>`，B 机器 `qrfile pull <输出目录>`。
> 记得住这两条就够了，其余全自动。详见 [docs/LIVE.md](docs/LIVE.md)。

## 三个承诺

1. **源文件只读**，绝不修改 —— 运行期有审计钩子强制，事后有指纹比对证明，源码有静态检查守着（见下）。
2. **还原后与原文逐字节一致** —— 四层校验，失败即关闭，不写任何半成品。
3. **目录结构完整保留** —— 含空目录、中文/emoji 文件名、CRLF/BOM 原样不动。

## 安装

```bash
pip install .
```

需要 Python ≥ 3.11。依赖：`segno`（编码）、`zxing-cpp`（解码）、`pillow`、`reportlab`、`charset-normalizer`、`click`。

### 气隙环境离线安装

`zxing-cpp` 提供 **abi3 wheel**（`cp312-abi3`），在 Python 3.12/3.13/3.14 上通用，Windows amd64 和 Linux x86_64 都有预编译包，**不需要编译器和网络**：

```bash
# 在有网的机器上
pip download qrfile segno zxing-cpp pillow reportlab charset-normalizer click -d wheels/
# 把 wheels/ 拷进气隙机器
pip install --no-index --find-links wheels/ qrfile
```

### 打成单文件可执行程序（目标机器不用装 Python）

```bash
pip install pyinstaller
python packaging/build.py            # → dist/qrfile.exe（约 21 MiB）
python packaging/build.py --onedir   # 目录版，启动快得多，但要带一整个文件夹
```

打完之后脚本会**自动用产物跑一遍它自己的 `selftest --full`** —— PyInstaller 最常见的坑就是"打包成功但运行时缺模块"，不实测等于没打。

Linux 上推荐用专用脚本（会先检查 tkinter、建 venv、装依赖）：

```bash
bash packaging/build_linux.sh            # → dist/qrfile（没有 .exe）
bash packaging/build_linux.sh --onedir
```

PyInstaller **不能跨平台交叉编译**：Windows 的 exe 只能在 Windows 上打，Linux 的
ELF 只能在 Linux 上打。Linux 版建议在目标发行版或更老的发行版上构建（glibc 兼容）。

有两个包必须显式收集，不然运行到对应功能才炸：`charset_normalizer`（有 mypyc 编译的子模块和数据表）和 `reportlab`（生成 PDF 要读自带字体数据）。

**部署注意点**（都是实测踩到的，不是猜的）：

- **单文件版启动时要往 `TEMP` 解压自己**，所以目标机器得有可写的临时目录。实测把 `TEMP`/`TMP` 拿掉后会直接报 `Could not create temporary directory!`。受限环境请用 `--onedir` 版本（它不自我解压，启动也快得多）。
- 单文件版每次启动都要解压（约 1 秒），频繁调用的话 `--onedir` 体验好很多。
- Windows Defender 偶尔会误报单文件 exe（自解压行为像加壳）。加个排除项即可，或者用 `--onedir` 版本。

> 产物是自包含的：实测把环境里所有 `PYTHON*` 变量清掉后仍能正常运行，`selftest` 全过。

## 命令

| 命令 | 作用 |
|---|---|
| `encode <路径...> -o <目录>` | 编码成二维码 PNG 序列（可加总览图 / PDF） |
| `decode <图或目录...> -o <目录>` | 还原成文件树 |
| `plan <路径...>` | **只算不生成**：码数、体积、预估扫描时长、哪些文件会被跳过 |
| `verify <源> <二维码目录>` | 还原到内存里跟源逐文件比对，不写任何文件 |
| `info <二维码目录>` | 只读分片头，列出会话与缺片情况 |
| `selftest [--full]` | 内置自检：合成语料跑完整往返 + 故障注入 |

**退出码**：`0` 成功 · `1` 部分跳过但成功 · `2` 校验失败 · `3` 输入错误 · `4` 内部错误。

## 选 profile：这决定"能不能扫出来"

| profile | 模块数 | 每码净载荷 | 抗梯形畸变 | 用途 |
|---|---|---|---|---|
| `camera` | 77 (v≤15) | 260 B | **5%** | 手机实时扫屏幕，最抗畸变 |
| **`screen`（默认）** | 97 (v≤20) | 826 B | **5%** | 屏幕显示 + 拍照识别 |
| `print` | 137 (v≤30) | 1338 B | 0%（需正视） | A4 打印后扫纸 |
| `max` | 177 (v≤40) | 2921 B | 0%（需正视） | 纯数字归档，不经摄像头 |

**模块越少越抗畸变**（模块大 = 容错余量大）。屏幕链路取景难控制，所以默认用 `screen`；打印时几何形状你能完全控制，可以放心用 `print`。

⚠️ **屏幕是瓶颈，不是打印。** v40 在 380px（≈2px/模块）下手机直接读不出来，1080px 才行。而 A4 上 0.4mm/模块就能装下 v40 —— 纸面反而更宽松。

### 实际吞吐量（`plan` 会算给你看）

| 链路 | 单码载荷 | 估计吞吐 | 实用上限 |
|---|---|---|---|
| 屏幕 + 手机 | 826 B | ≈ **20 KB/分钟** | 压缩后 ≲ 300 KB |
| 打印 + 手机 | 1338 B | ≈ **35 KB/分钟** | 压缩后 ≲ 1 MB |
| 纯数字归档 | 2921 B | CPU 限制 | 单文件 8 MiB |

屏幕链路适合百 KB 级的文本（源码、配置、密钥、文稿片段）。上 MB 的请用 `--profile print`，或者**开总览图**——一张照片扫下一整片，这是最实用的提速手段。

> **别把两个时间搞混**：`plan` 里「本机编码耗时」是程序自己要跑多久（1.5 MB 约 30 秒），
> 「预计人工扫描」是你拿手机一张张扫完要多久（同一个文件约 23 分钟）。**卡人的是后者。**

## 减少采集次数：`--screens`（一屏多码）

默认是"一张码 = 一次扫描"，2 MB 文本要 430 张照片 —— 这不合理。用 `--screens`
按**整屏排版**，一屏塞满码，拍一张照片解一屏：

```bash
qrfile plan   big.json                          # 先看要拍几张
qrfile encode big.json -o out --screens         # 产出 screen_001.png ...
# 把 screen_*.png 全屏显示，一张张拍
qrfile decode ./照片目录 -o restored             # 照片丢进去就还原
```

**实测的硬约束**（模拟手机拍屏：斜 0.6° + 相机 2 倍采样 + 镜头模糊 + 噪声 + JPEG）：

> 决定成败的是**每个模块分到几个相机像素，阈值约 2.5** —— 跟它在屏幕上多大无关。
> ≤2.0 一律解不出（被摩尔纹和非整数重采样打垮），≥2.5 稳定。

手机拍照时屏幕占满画面、相机分辨率约为屏幕像素数的 2 倍，所以屏幕上 3 px/模块
≈ 相机 6 px/模块，有 2.4 倍余量。

| 1920×1080 屏 | 每屏张数 | 每屏载荷 | 2 MB 文本需要 |
|---|---|---|---|
| 现在（一次一张） | 1 | 0.8 KB | 430 张照片 |
| **`--screens` 默认（3 px/模块）** | **5×3 = 15** | **12.1 KB** | **29 张照片** |
| `--screens --module-px 2`（激进） | 8×4 = 32 | 25.8 KB | 14 张照片 |

2 px/模块 是我测出来的极限，但**真实屏幕有 RGB 次像素结构，我的模拟没建模**，
所以默认用稳妥的 3，不建议直接上 2。

**为什么不做彩色码**：QR 的数据密度已经是 0.73 bit/模块（用掉约 73% 面积），
换成自研黑白码最多快 23%；真正的杠杆是颜色（1→2~3 bit/模块），但要对抗白平衡
漂移、屏幕伽马、摩尔纹、色渗，风险很高，收益（29 张 → 14 张）远不如改用视频。

**再降一个数量级的方向**是视频 + 喷泉码：屏幕播放动画、手机录一段像，每帧就是一
整屏；喷泉码让丢帧无所谓。这是 [qrsend](https://github.com/igarinpiano/qrsend)
那类工具的做法，代价是要实现视频生成、抽帧和纠删编码。还没做。

## 一张二维码最多能装多少？为什么大文件要出很多张

**这是二维码的物理上限，不是软件限制。** ISO/IEC 18004 规定的最大二维码是
version 40（177×177 模块），字节模式下装 **2953 字节**（纠错 L）。减掉 32 字节
分片头，**每张码最多装 2921 字节**。没有任何办法突破。

所以 **1.5 MB 的文件至少要 88 张码**（压到 251 KB 后）。想让一个文件进一张码，
只有两条路：文件小于约 2.9 KB，或者不用二维码。

### 怎么让张数最少

两个旋钮，都是直接乘上去的：

```bash
qrfile encode big.json -o out --profile max --compression auto
```

| 组合 | 1.5 MB JSON 实测张数 |
|---|---|
| 默认（`screen` + `auto`） | **309 张** |
| `screen` + `zlib`（旧默认） | 379 张 |
| `max` + `zlib` | 108 张 |
| **`max` + `auto`** | **88 张** |

- **`--compression auto`（默认）**：把 zlib 和 lzma 都跑一遍取最小的。
  对这个文件 zlib 压到 20.8%、lzma 压到 16.9%，等于白捡 18% 的张数。
  代价是压缩多花 0.2 秒。
- **`--profile max`**：每张码从 826 字节涨到 2921 字节，张数少 3.5 倍。
  **但每张码难扫得多** —— 实测 v40 对拍歪的容忍度是 **0%**（`screen` 有 5%），
  而且手机上至少要 1080px 才认得出。所以"张数少"不等于"总时间短"。

`plan` 现在会**真的压一遍算出准确张数**，不再是估算（以前按"假设压到 30%"估，
1.5 MB 的文件估 547 张、实际 379 张，差 44%）。

## 支持与不支持的文件类型

判定**基于内容**（magic number + 编码探测 + 熵护栏），不看扩展名。扩展名只在内容判不出来时当平手的提示，永远不能推翻内容证据。

**支持**（内容判定为文本）：

- 无 BOM 的 ASCII / UTF-8；带 BOM 的 UTF-8 / UTF-16 LE·BE / UTF-32 LE·BE
- **GB18030 / GBK / GB2312** —— 中文环境刚需
- Big5 / Shift-JIS / EUC-KR（需 `--text-encodings`）
- CP1252 / Latin-1（低置信度兜底，会给警告）
- 任意换行风格（CRLF / LF / CR / 混合）—— **原样保留**
- 源码、配置、日志、CSV/TSV、Markdown、JSON/XML/YAML/TOML、i18n 资源、`Makefile`、**SVG**（是文本不是图片）

**跳过并提醒**：

| 类别 | 例子 | 判定依据 |
|---|---|---|
| 位图 | PNG/JPEG/GIF/BMP/WebP/HEIC/TIFF | magic |
| 音视频 | MP3/MP4/MKV/WAV/FLAC/AVI | magic |
| 压缩包 | ZIP/RAR/7z/GZ/BZ2/XZ/TAR | magic |
| **Office OOXML** | **docx / xlsx / pptx / jar / apk / odt / epub** | **本质是 ZIP** |
| 二进制文档 | PDF / DOC / XLS / PPT(旧) / SQLite | magic |
| 可执行 / 库 | EXE/DLL/SO/DYLIB/A/O/CLASS/PYC/WASM | magic / 扩展名 |
| 字体 | TTF/OTF/WOFF/WOFF2 | magic |
| 序列化二进制 | 裸 Protobuf / Avro / Parquet / **Pickle** / **MsgPack** / BSON | NUL + 扩展名 |
| 高熵数据 | 无扩展名但熵接近 8 bit/byte（加密块、密钥） | 熵估计 |
| 符号链接 | — | 默认只记录不跟随（`--follow-symlinks` 可跟随） |
| 特殊文件 | FIFO / 设备节点 / socket | `stat` 类型 |

**最容易混的三组**：

- Pickle / MsgPack / BSON **是二进制，跳过**；JSON / XML / YAML / TOML **是文本，支持**
- **SVG 是文本**，不是图片
- **`.docx` 是 ZIP**，不是文本

被跳过的文件会逐条打印 `SKIP <路径> — <原因>`，并写进清单的 `skipped` 字段 —— 解码端能告诉你"当初跳过了什么"。

## 上限

| 项 | 默认 | 说明 |
|---|---|---|
| 单文件大小 | 8 MiB | `--max-file-size` |
| 单会话文件数 | 5000 | `--max-files` |
| 单会话总字节 | 64 MiB | `--max-total-bytes` |
| 目录深度 | 64 | `--max-depth` |
| 相对路径长度 | 1024 字节 | `--max-path-len` |
| 文件名长度 | 255 字节（NTFS 上限） | `--max-name-len` |
| 分片索引 | uint16 ⇒ 单文件最多 65535 片 | 物理硬上限 |

**两类超限的处理方式刻意不同**：

- **单个文件的问题**（太大、路径太长、名字非法、不是文本）⇒ 跳过它、记下原因、继续跑，最后退出码 `1`。
- **整个会话的预算超了**（文件数 / 总字节）⇒ **直接报错**。因为这会悄悄改变归档的含义 —— 用户以为整棵树都进去了，实际只进去一半。这种事必须大声说出来。

**压缩**默认开（zlib level 9）。文本通常压到 **20~35%**，码数直接降到 1/3。压不动的数据（已经压缩过的、随机的）会自动不压。

⚠️ 大文件 / 大目录的分包、纠删冗余、喷泉码**没有实现** —— 这类场景少见，复杂度和风险不值当。超限时会明确报错并建议你分几次编码不同的子目录。

## 源文件只读（硬约束）

做成三层，不是口头承诺：

1. **唯一的读取入口** —— 全代码库只有 `readonly.py` 里的 `read_bytes` / `read_prefix` / `iter_file_bytes` 能打开源文件，永远是 `O_RDONLY`（Linux 上尽力用 `O_NOATIME`）。临时文件一律进系统临时目录或输出目录，**绝不在源文件旁边落 `.tmp`**。
2. **运行期审计钩子** —— 通过 `sys.addaudithook` 在系统调用级拦截：encode 期间任何以写意图触碰源路径的操作**当场抛异常**。这给的是"运行时可证明"，不是"我们小心点"。
3. **事后指纹比对** —— 读之前和写完之后各采一次源树全量指纹（路径 / 大小 / mtime_ns / 权限 / SHA-256）并逐项比对，**哪怕只是 mtime 变了也报错**，并指名道姓说哪个文件的哪个字段变了。顺带覆盖读取期间被外部改动的 TOCTOU 情况。

另外，**解码端**专门防"从输出侧改到源文件"：

- `-o` 指向源目录、或其祖先/后代 ⇒ **拒绝**
- 目标已存在且是**硬链接** ⇒ 拒绝（写它等于改到别处的同一份内容）
- 目标位置已存在**符号链接** ⇒ 拒绝跟随（会逃出输出目录）
- 默认**拒绝覆盖**已存在文件（需 `--overwrite`）
- 输出目录里的"多余"文件**一律不删** —— 只创建和写入

## 验证体系

> 原则：验证不是可选项，解码端**失败即关闭** —— 任何一片不合格，一个字节都不写盘。

- **V0 输入指纹**（编码入口）：全程 `open(p,'rb')` 读原始字节，从不文本模式、从不转编码、从不规范换行、从不剥 BOM。逐文件记 SHA-256。
- **V1 编码期自验证**（编码出口，强制）：每张 PNG 写出后**立刻解回来逐字节比对**。能抓到编码器 bug、纠错等级容不下载荷、缩放/插值导致的模块畸变。
- **V2 分片级完整性**（解码期）：每片自带 8 字节会话号 + 索引 + 总数 + CRC32。精确报错：`缺少分片 3, 7, 12（共 17 片）`、`分片 5 两次内容不一致`、`发现 2 个不同会话`。重复片内容一致则容忍（同一张扫两次很常见）。
- **V3 还原级校验**（解码出口，强制）：逐文件重算 SHA-256 与大小 + 布局自洽 + 集合级 `archive_sha256`（证明"有哪些文件"这件事本身没被动过）。
- **`selftest --full`**：合成语料跑完整往返，外加故障注入（删片 / 涂改 / 复制 / 无关码 / 篡改内容），断言每种都被精确报出。

### 那一层真的抓到过东西

第一次端到端跑就炸了：`清单偏移不自洽：'bom.txt' 的 offset 是 4079，应该是 26`。

根因是排序不一致 —— BLOB 按**原始路径**顺序拼，而清单按 **path_b64** 排序。`big.txt` 原始路径在前，但 base64 后 `Ym9t`(bom) < `Ymln`(big)，因为 `'9' < 'l'`，于是偏移量整体错位，还原时会张冠李戴。**V3 的 `verify_layout` 在写盘前就拦下了它，一个错误字节都没出去。**

## 已知边界（如实说明，不含糊）

| 边界 | 说明 |
|---|---|
| **梯形畸变 ≥10%** | **解不出来**。实测四种 binarizer、放大 2×、四个 profile 全试过，都无效 —— 透视纠正需要重写检测器，复杂度不值当。**手别太斜（≤5%）就没事**，或改用 `--profile camera`。 |
| **访问时间 (atime)** | Linux 上读取会更新 atime（除非挂载选项是 `noatime`/`relatime`）。工具尽力用 `O_NOATIME` 规避（需文件属主或 `CAP_FOWNER`），拿不到时会警告。Windows 的 NTFS 默认关闭 last-access 更新，通常无此问题。 |
| **无 BOM 且非 ASCII 的 UTF-16** | 探测不到，会被判成二进制并明确报出。这种文件极少见。 |
| **Windows 符号链接** | 创建符号链接需要开发者模式或管理员权限。目录链接会自动回退到 **junction**（`mklink /J`，不需要特权）；文件链接没有等价物，会如实报"没能重建"，**绝不伪造一个普通文件冒充链接**。 |
| **跨平台非 UTF-8 文件名** | POSIX 上 `caf\xe9.txt` 这类名字能无损往返（走 `path_b64` 原始字节）；但这样的清单拿到 Windows 上还原，会得到一个合法但名字略有出入的路径。 |
| **大小写冲突** | `File.txt` 和 `file.txt` 在 Linux 是两个文件、Windows 是一个。编码阶段就会检测并警告（`--strict` 下直接中止）。 |
| **`--jobs`** | 没有实现。编码是串行的；实测速度够用，加一个空转的参数不如不加。 |

## 实测数据速查

容量（QR v40 = 177×177，字节模式）：

| ECC | 单码容量 | profile |
|---|---|---|
| L | **2953 B** | `screen`(v20) / `max`(v40) |
| M | 2331 B | `print`(v30) |
| Q | 1663 B | `camera`(v15) |
| H | 1273 B | — |

载荷编码对比（同样一张 v40-L 码能装多少文件数据）：

| 编码 | QR 模式 | 每码字节 | 相对效率 |
|---|---|---|---|
| **裸字节** | Byte | **2953** | **100%** |
| Base45 | Alnum | 2864 | 97.0% |
| Base32 | Alnum | 2685 | 90.9% |
| Base64 | Byte（被迫） | 2214 | 75.0% |

选了裸字节模式 —— 容量最高、实现最简单。（Base45 的字母表恰好等于 QR 字母数字模式字符集，但算下来仍比裸字节少 3%。）

**解码器**：只用 `zxing-cpp`。实测密集码（1113 字符，65 个样本）通过率 zxing-cpp **59/65**，而 OpenCV 的 `QRCodeDetector` 是 **0/65** —— 所以**不做降级链**，把 0% 通过率的库放进去只会制造静默失败。zxing-cpp 是硬依赖，缺了会明确报错。

文本判定的**熵阈值 6.0** 是实测标定的：英文 ASCII 4.44、UTF-8 中文 5.16、GBK 中文 5.16、base64 文本 5.60（是文本，要放行）、zlib 压缩 6.37（是二进制，要拦住）、随机字节 7.98。6.0 正好卡在中间，两边余量都够。
