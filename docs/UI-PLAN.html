01 · Executive Summary

执行摘要

上一版 UI 已撤回。问题不在“有没有窗口”，而在于它仍然是 CLI 的附属品： 用日志当反馈、用 Tab 平铺功能、用布尔值管理任务生命周期。本方案从产品形态重新出发。

实施状态（2026-11-07） M0 已验证：PySide6 6.9.3 的 Qt6Core 依赖 GLIBC_2.28，RHEL 8 可用； M1 结构化事件层、M2 主框架、M3 发送流程、M4 接收流程已落地为 0.7.0 初版； M5（区间弹窗完善、诊断/错误卡片）与 M6（Windows 打包、视觉回归）继续推进。

核心判断

  • 不是表单，是任务流。 用户的目标只有两个：把文件送出去、把文件收回来。界面应围绕这两个任务组织，而不是围绕命令参数。
  • 角色先行。 发送机器和接收机器是两个完全不同的工作场景，首页必须先让用户选角色，再进入对应流程。
  • 状态必须可视化。 传输的核心信息是“收了多少、缺哪些、下一步做什么”。分片热力图比滚动日志更有效。
  • UI 不解析日志。 新增结构化事件层，CLI 和 GUI 消费同一套 TransferEvent，避免脆弱的 stdout 抓取。

建议方案

  • 技术栈： PySide6 / Qt 6 LTS 作为主界面；Phase 0 先在 RHEL 8 + Windows 11 上做打包与 glibc 验证。
  • 进程模型： 主界面常驻，全屏播放器作为独立子进程；事件通过 NDJSON / 本地 IPC 回流。
  • 交付策略： 先做核心事件层，再做页面；CLI 保持不变，GUI 可随时回退。
  • 周期： 约 32–37 人日（单人 6–8 周），7 个里程碑。
一句话结论 先把“传输任务状态”做成可复用、可测试的核心，再用 Qt 做一层薄而清晰的界面； 不要在 Tk 里继续堆控件，也不要让 UI 依赖控制台输出。

02 · Post-mortem

上一版 UI 复盘

上一版实现的核心问题可以归为五类：信息架构、反馈方式、生命周期、技术约束、交付方式。 下表按“现象 → 根因 → 本方案对策”列出。

现象根因影响本方案对策
发送、接收、诊断挤在三个 Tab 里 按“功能”而不是按“任务/角色”组织信息 发送机器 / 接收机器场景混淆，首次使用者不知道先做什么 角色首页 + 发送/接收两条独立向导
底部日志是主要反馈 子进程 stdout 直接倾倒进文本框 进度不可读、错误不可操作、用户被迫读控制台 结构化事件 + 进度环 + 分片热力图 + 错误卡片
按钮启停靠一个 running 布尔值 没有显式任务状态机 停止、重试、关闭窗口的边界行为不稳定 Idle → Preparing → Playing/Receiving → … → Done 状态机
全屏播放器与主窗口抢焦点 播放器、主界面、日志在同一个事件循环里 播放时主界面无响应；VNC 下键盘行为不可预测 播放器独立子进程；主界面只做监控与区间控制
文件选择只能填一个路径 没有原生对话框、拖拽、最近记录 重复操作多，易输错路径 QFileDialog + 拖拽 + 最近路径 + 参数记忆
GUI 打包进 console exe 一个入口同时承担 CLI 和 GUI 双击出现黑色控制台窗口，体验割裂 拆分 qrfile（console）与 qrfile-gui（windowed）
进度用 \r 覆盖同一行 CLI 输出协议不是为 UI 设计的 管道里 \r 堆积，日志难以阅读 事件层直接传出 received/total，UI 自己渲染
错误只弹 messagebox 没有错误分类与恢复动作 用户只知道“失败了”，不知道下一步 错误卡片：人话 + 原因 + ≤3 个动作 + 可展开详情
测试只覆盖窗口构造与参数拼接 UI 逻辑与 Tk 强耦合 交互回归、DPI、跨平台问题无法提前发现 状态机单测 + offscreen 组件测试 + 截图回归 + E2E
结论 继续在 Tk 上打补丁的边际收益很低。下一版需要同时调整交互模型和 技术底座，但可以保留现有编码/解码/抓屏核心不动。

03 · Goals

目标与非目标

目标（v1 必须满足）

  • 5 分钟上手： 从打开程序到开始传输，不需要阅读文档。
  • 状态可回答： 任何时刻都能看到“在做什么、进度多少、缺什么、下一步”。
  • 行为一致： GUI 与 CLI 使用同一套核心逻辑、错误码和文案。
  • 离线可用： 不依赖网络、CDN、在线字体或云服务。
  • 跨平台： Windows 10/11 与 RHEL 8 / Ubuntu 桌面。
  • 可回退： GUI 出问题时，用户仍可继续使用现有 CLI。
  • 可测试： 状态、事件、关键页面都有自动化测试。

非目标（v1 明确不做）

  • 不做移动端、远程 Web 控制台或多人协作。
  • 不重构二维码编码、压缩、校验算法。
  • 不做多任务并行传输；v1 一次只跑一个任务，但保留队列接口。
  • 不做账号体系、云端同步、自动更新。
  • 不把静态 PNG 的 encode/decode 塞进首批页面；后续可加独立页签。
  • 不在 v1 强制把全屏播放器迁移到 Qt；先保留独立进程方案。

05 · Principles

设计原则

01角色先行

第一屏不问参数，只问“这台机器是发送机器还是接收机器”。角色决定后续页面、默认值和可用的诊断项。

02一条主线

发送和接收各是一条向导式主线：选择内容 → 设置 → 运行 → 完成。高级参数折叠，不打断主线。

03状态可见

用状态机驱动界面。每个状态都有明确的标题、颜色、可执行动作，不靠用户从日志里猜。

04错误可行动

错误卡片最多给三个动作：重试、改设置、打开诊断。原始堆栈放在“详情”里，不默认展示。

05渐进披露

默认只显示最常改的 2–3 个选项；帧率、模块像素、压缩器、采集后端放进“高级”。

06离线优先

所有资源内置，不引用 CDN、在线字体或远程接口。UI 在完全断网的机器上必须完整可用。

07键盘可用

Tab 遍历、Enter 主操作、Esc 返回/结束、空格暂停。全屏播放器保留现有快捷键。

08与 CLI 同源

GUI 与 CLI 共用核心服务、事件、错误码和文案。GUI 不是第二套实现。

07 · Mockups

效果图

以下为高保真交互稿示意（HTML/CSS 渲染，非最终像素稿）。所有页面共享同一套侧栏、 卡片、状态色与 8px 间距体系；分辨率基准 1440×900，支持 125% / 150% 缩放。

7.1 首页 / 角色选择

角色优先不要求用户理解参数，只需要知道“这台机器负责发还是收”。
最近任务重复传输可一键继续；失败任务保留缺片状态，直接进入区间修复。
环境状态把 doctor 的关键结论前置到首页，异常项可点击进入诊断。

7.2 发送设置

拖拽 + 原生对话框目录、文件都可直接拖入；路径错误在进入下一步前就被拦截。
预估而非术语用户关心“要多久、多少屏”，而不是版本号、模块像素。
默认值可记忆上次使用的模式、时长、目录写入设置，下次自动带出。

7.3 发送监控

进度环 + 本轮长文件以“轮”为单位更直观；同时显示分片级进度，避免误以为要等很久。
区间就地操作接收机器报缺片后，不需要退出播放器；在监控页输入范围即可切换。
事件流而非日志底部只保留结构化事件，可按级别过滤；原始日志在诊断页导出。

7.4 接收监控

缺片是主状态橙色热力图 + 范围文本 + 一键动作，把“补片”从故障处理变成常规操作。
自动窗口可见明确显示当前采集的是哪个窗口、分辨率多少，可一键更换。
校验前置收齐后直接显示“校验中 / 已写 0 文件”，让用户知道还没有落盘。

7.5 播放区间

即时解析边输入边校验，显示分片数、页数、预计单轮时长。
自动适配按当前布局的 per_screen 映射整页；一屏多码无需用户关心。
安全恢复“恢复完整播放”始终可用；输入无效时播放器保持原状态。

7.6 诊断与错误处理

动作导向每个错误最多三个动作，直接调用现有能力，不让用户去查文档。
环境卡片化把 doctor 的文本输出变成可扫读的通过/警告/失败卡片。
可导出一键打包日志、配置、环境信息，方便远程支持。

为什么推荐 PySide6

  • 原生控件、成熟的布局系统、高 DPI 支持，能直接实现本报告的效果图。
  • 文件对话框、拖拽、进度条、表格、主题、键盘导航开箱即用。
  • LGPL 许可，与 MIT 项目兼容；Qt 6 LTS 维护周期长。
  • 全屏播放器后续可迁移到 Qt，去掉 tkinter 依赖，统一事件循环。
  • 可用 QT_QPA_PLATFORM=offscreen 做无头 UI 测试。

风险与前置验证（Phase 0）

  • RHEL 8： 用 PySide6 6.5+ manylinux_2_28 wheel + PyInstaller 打包，检查 glibc、字体、X11 插件。
  • Windows 11： 检查 125% / 150% DPI、深色主题、任务栏图标、窗口最大化。
  • 包体： 记录 onefile / onedir 体积和启动时间；必要时裁剪 Qt 模块。
  • 回退： 若 Spike 失败，降级为 ttk 重设计（保留本报告的 IA 与流程，降低视觉目标）。
决策门槛 Phase 0 必须在真实 RHEL 8 和 Windows 11 上各跑通一次：启动、中文显示、文件对话框、 全屏窗口、抓屏、打包产物自检。任一项失败则切换到回退方案，避免在中期才发现不可交付。

进程模型（分阶段）

Phase 1 · 低风险 主界面 Qt 进程；发送播放器仍为 tkinter 子进程，通过 NDJSON 事件回流；接收逻辑可直接在 Qt 应用内运行（无全屏窗口冲突）。
Phase 2 · 统一 将全屏播放器迁移到 Qt（QWidget + QImage），去掉 tkinter 依赖；同一事件循环，支持暂停、区间切换、快捷键。

打包策略

  • 两个入口： qrfile（console，保留 CLI）与 qrfile-gui（windowed，双击无黑窗）。
  • 共享核心： 两个入口打包同一份 qrfile 包，避免逻辑分叉。
  • 体积策略： 默认 onefile 便于分发；提供 --onedir 给启动速度和体积敏感场景。
  • 离线依赖： Qt 插件、字体、图标全部内置；不引用外部 CDN。
  • 兼容性： 在目标发行版或更老的发行版构建，记录 glibc 基线。

12 · Testing

测试与验收

测试分层

  • 单元测试： 状态机、事件序列化、区间解析、参数校验、路径安全。
  • 组件测试： pytest-qt + QT_QPA_PLATFORM=offscreen，覆盖热力图、进度环、错误卡片。
  • 视觉回归： 关键页面在 100% / 125% / 150% 下截图比对，允许阈值内差异。
  • 端到端： 单机双进程（播放窗口 + 采集区域）或录屏帧序列，验证还原一致。
  • 跨平台： Windows 10/11、Ubuntu 24.04、RHEL 8；X11 与 Wayland 各跑一次。
  • 无障碍： 仅键盘完成发送/接收；高对比主题；控件有可读名称。

性能与体验预算

  • 空闲 CPU < 3%；进度更新 ≤ 10 Hz，避免 UI 抖动。
  • 事件处理单次 < 16 ms；热力图增量更新，不整页重绘。
  • 主界面内存 < 300 MB（不含播放器/解码缓存）。
  • 从点击“开始播放”到全屏窗口出现 < 1.5 秒。
  • 接收机器停止后 2 秒内释放窗口/抓屏资源。
  • 所有可交互控件支持 Tab 聚焦，焦点环清晰可见。
Definition of Done 功能完成 + 单元/组件测试通过 + 目标平台截图基线更新 + 文档更新 + 打包产物自检通过 + 在真实发送机器 / 接收机器上完成一次端到端传输。

13 · Risks

风险与对策

风险概率影响对策
PySide6 在 RHEL 8 打包失败或依赖 glibc 过高中高M0 先验证；失败则切换 ttk 重设计，IA 与流程不变，仅降低视觉目标
包体从 30 MB 增至 150–200 MB高中提供 onedir 构建；裁剪 Qt 模块；在文档中说明体积与启动速度取舍
全屏播放器与主界面焦点冲突中高Phase 1 保持播放器独立子进程；主界面不抢焦点；Esc/停止路径单独测试
接收时 GUI 自身被截入画面中中接收页提供“最小化自身”选项；优先按窗口标题定位；整屏时把 GUI 移到副屏或最小化
高 DPI / 字体导致布局错位中中Qt 高 DPI 策略 + 三档缩放截图回归；使用弹性布局，禁止固定像素宽度
事件层重构影响 CLI 行为中高CLI 输出保持兼容；事件层先旁路接入；全量 CLI 回归测试作为门禁
UI 测试不稳定中中offscreen + 固定数据；视觉回归允许阈值；E2E 使用录屏帧而非实时抓屏
范围蔓延到静态二维码 / 云功能中低v1 明确非目标；新需求进入 backlog，按 P1/P2 排期

14 · Decisions

待决策事项

需要评审确认

  • 目标平台优先级： 先 Windows 接收机器，还是先 RHEL 8 发送机器？建议先 Windows。
  • 技术栈： 是否接受 PySide6（包体 +120–180 MB）？若不接受，是否接受 ttk 的视觉上限？
  • 播放器迁移： v1 是否保持 tkinter 播放器子进程？建议保持，Phase 2 再迁移。
  • 打包形态： 两个入口（推荐）还是一个 exe 加参数？
  • 语言： v1 只做中文，还是同时预留英文资源？

建议的默认答案

  • 先 Windows 11 接收机器，再 RHEL 8 发送机器。
  • 采用 PySide6；M0 失败再回退 ttk。
  • v1 保留 tkinter 播放器子进程，Qt 只做控制台。
  • 两个入口：qrfile + qrfile-gui。
  • 中文优先，文案集中管理，预留 i18n 接口。
